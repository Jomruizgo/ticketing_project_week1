La feature de asignación de oportunidades abarca el CRUD Service (crud_service/) para persistencia y lógica de dominio, y consume eventos de RabbitMQ. La arquitectura es hexagonal: Domain, Application, Infrastructure, Api. Usar .NET 8 con EF Core para PostgreSQL. Crear la entidad WaitlistOpportunity en Domain con campos: Id, WaitlistEntryId, TicketId, Status (pending/active/consumed/expired/failed), ActivatedAt, ExpiresAt. Definir el enum OpportunityStatus con transiciones permitidas: Pending→Active, Pending→Failed, Active→Consumed, Active→Expired. Implementar el puerto IPrioritizationStrategy en Domain/Interfaces con un adaptador FifoStrategy en Infrastructure que consulta la inscripción activa más antigua para el evento. Crear AssignOpportunityCommand y AssignOpportunityHandler implementando IAssignOpportunityUseCase en Application/UseCases. El handler: (1) consulta IPrioritizationStrategy por el siguiente comprador elegible, (2) si no hay ninguno, devuelve un resultado 'no eligible' al llamador (el llamador es responsable de gestionar la devolución del ticket al inventario, ver más abajo), (3) si encuentra uno, crea WaitlistOpportunity con estado Pending (persistido de inmediato para trazabilidad), (4) llama a ITicketReservationPort para reservar temporalmente la entrada, (5) si la reserva falla, transiciona la oportunidad a Failed mediante TransitionTo (Pending→Failed), registra el incidente y retorna (la inscripción permanece activa para el siguiente intento), (6) si la reserva tiene éxito, transiciona la oportunidad a Active mediante TransitionTo (Pending→Active), establece expiresAt = now + TTL, marca la inscripción como inactive, publica el mensaje DLX a q.waitlist.opportunity.delay (el TTL comienza desde la activación, no desde la creación) y notifica mediante IOpportunityObserver (patrón Observer). Definir el puerto IOpportunityObserver en Domain/Interfaces. Crear TicketReleasedConsumer en Infrastructure/Messaging que escucha la routing key ticket.released e invoca el caso de uso. El consumer hace ACK en éxito o fallo de negocio, NACK con requeue:false en fallo técnico. Cuando el handler devuelve 'no eligible', el consumer publica el evento ticket.returned_to_inventory (routing key: ticket.returned_to_inventory, exchange: tickets, payload: { ticketId, eventId, returnedAt }) para que ReservationService transite el ticket de released a available para compra directa. La oportunidad se publica a la cola DLX q.waitlist.opportunity.delay con TTL, dead-lettered a q.waitlist.opportunity.expired. La tabla waitlist_opportunities usa columnas en snake_case.
