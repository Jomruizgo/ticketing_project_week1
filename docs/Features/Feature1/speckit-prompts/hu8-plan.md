Esta HU tiene dos partes: un caso de uso backend (ClaimOpportunity) y la UI frontend de estado/acción. BACKEND: La feature de reclamación vive en el CRUD Service (crud_service/), arquitectura hexagonal: Domain, Application, Infrastructure, Api. Usar .NET 8 con EF Core para PostgreSQL. Crear ClaimOpportunityCommand (OpportunityId, BuyerEmail) y ClaimOpportunityHandler implementando IClaimOpportunityUseCase en Application/UseCases. El handler: (1) carga la oportunidad por ID desde IWaitlistOpportunityRepository, (2) si no se encuentra, devuelve null (el controller mapea a 404), (3) valida que opportunity.Status sea Active (si no, devuelve conflicto → controller mapea a 409), (4) valida que buyerEmail coincida con el correo de la inscripción (si no, devuelve prohibido → controller mapea a 403), (5) valida que expiresAt > DateTime.UtcNow (si expiró, devuelve conflicto), (6) transiciona el estado a Consumed mediante WaitlistOpportunity.TransitionTo (Active→Consumed del patrón State), (7) guarda la oportunidad actualizada, (8) devuelve ClaimOpportunityResponse con opportunityId, ticketId, eventId, status 'consumed'. WaitlistController expone POST /api/waitlist/opportunities/{id}/claim recibiendo { buyerEmail } y delega al puerto del caso de uso. TDD: prueba unitaria del handler para happy path (active → consumed), rechazo de oportunidad expirada, rechazo por correo incorrecto, idempotencia de oportunidad ya consumida. Prueba de integración con Testcontainers verificando que la transición de estado persiste correctamente. FRONTEND: La feature de estado y acción vive en el directorio frontend/, una aplicación Next.js con React, TypeScript, Tailwind CSS y componentes shadcn/ui. Crear el componente WaitlistStatus en components/ que acepta eventId y buyerEmail como props. Al montar, llama a GET /api/waitlist/entries?eventId={id}&email={email} mediante una nueva función getWaitlistStatus(eventId, email) agregada a lib/api.ts. Agregar el tipo WaitlistStatusResponse a lib/types.ts: { entry: WaitlistEntryResponse, opportunity?: { id: number, ticketId: number, status: string, activatedAt: string, expiresAt: string, remainingMinutes: number } }. El componente renderiza condicionalmente: (a) si entry.status === 'active' y sin oportunidad → mostrar badge 'En espera', (b) si opportunity.status === 'active' → mostrar cuenta regresiva (useEffect con intervalo calculando tiempo restante desde expiresAt), mostrar botón 'Avanzar al pago', (c) si opportunity.status === 'consumed' → mostrar badge 'Oportunidad utilizada', (d) si opportunity.status === 'expired' → mostrar badge 'Oportunidad expirada'. Crear el hook useWaitlistSse(email) en hooks/ que se conecta a GET /api/waitlist/stream?email={email} usando la API EventSource. En el evento 'opportunity_activated', actualizar el estado para mostrar la oportunidad activa. En el evento 'opportunity_expired', actualizar el estado a expirada. La acción de reclamación llama a una nueva función claimOpportunity(opportunityId, buyerEmail) en lib/api.ts que hace POST a /api/waitlist/opportunities/{id}/claim. Manejar: 200 → redirigir a la página de pago con ticketId, 409 → mostrar toast 'La oportunidad ya no está activa', 403 → mostrar toast de error. La cuenta regresiva usa useEffect con setInterval(1000) calculando Math.max(0, differenceInSeconds(expiresAt, now)) y muestra el formato MM:SS; cuando llega a 0, deshabilitar el botón de reclamar. Integrar WaitlistStatus en la página de detalle del evento debajo o reemplazando WaitlistEnrollForm cuando el comprador ya tiene una inscripción activa. Seguir los patrones existentes de use-reservation-status.ts y use-payment-status.ts para hooks de polling y SSE.
