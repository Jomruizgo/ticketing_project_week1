This HU has two parts: a backend use case (ClaimOpportunity) and the frontend status/action UI. BACKEND: The claim feature lives in the CRUD Service (crud_service/), hexagonal architecture: Domain, Application, Infrastructure, Api. Use .NET 8 with EF Core for PostgreSQL. Create a ClaimOpportunityCommand (OpportunityId, BuyerEmail) and ClaimOpportunityHandler implementing IClaimOpportunityUseCase in Application/UseCases. The handler: (1) loads the opportunity by ID from IWaitlistOpportunityRepository, (2) if not found, returns null (controller maps to 404), (3) validates opportunity.Status is Active — if not, returns a conflict result (controller maps to 409), (4) validates the buyerEmail matches the enrollment's email — if not, returns forbidden (controller maps to 403), (5) validates expiresAt > DateTime.UtcNow — if expired, returns conflict, (6) transitions status to Consumed via WaitlistOpportunity.TransitionTo (Active→Consumed from the State pattern), (7) saves the updated opportunity, (8) returns ClaimOpportunityResponse with opportunityId, ticketId, eventId, status "consumed". The WaitlistController exposes POST /api/waitlist/opportunities/{id}/claim accepting { buyerEmail } and delegates to the use case port. TDD: unit test handler for happy path (active → consumed), expired opportunity rejection, email mismatch rejection, already-consumed idempotency. Integration test with Testcontainers verifying state transition persists correctly. FRONTEND: The frontend status and opportunity action UI lives in the frontend/ directory, a Next.js application with React, TypeScript, Tailwind CSS, and shadcn/ui components. Create a WaitlistStatus component in components/ that accepts eventId and buyerEmail as props. On mount, it calls GET /api/waitlist/entries?eventId={id}&email={email} via a new function getWaitlistStatus(eventId, email) added to lib/api.ts. Add WaitlistStatusResponse type to lib/types.ts: { entry: WaitlistEntryResponse, opportunity?: { id: number, ticketId: number, status: string, activatedAt: string, expiresAt: string, remainingMinutes: number } }. The component renders conditionally: (a) if entry.status === "active" and no opportunity → show "En espera" badge, (b) if opportunity.status === "active" → show countdown timer (useEffect interval computing remaining time from expiresAt), show "Avanzar al pago" button, (c) if opportunity.status === "consumed" → show "Oportunidad utilizada" badge, (d) if opportunity.status === "expired" → show "Oportunidad expirada" badge. Create a useWaitlistSse(email) hook in hooks/ that connects to GET /api/waitlist/stream?email={email} using EventSource API. On "opportunity_activated" event, update state to show active opportunity. On "opportunity_expired" event, update state to show expired. The claim action calls a new function claimOpportunity(opportunityId, buyerEmail) in lib/api.ts that POSTs to /api/waitlist/opportunities/{id}/claim. Handle: 200 → redirect to payment page with ticketId, 409 → show "La oportunidad ya no está activa" toast, 403 → show error toast. The countdown timer uses a useEffect with setInterval(1000) computing Math.max(0, differenceInSeconds(expiresAt, now)) and displays MM:SS format. When timer reaches 0, disable the claim button. Integrate WaitlistStatus into the event detail page below or replacing the WaitlistEnrollForm when the buyer already has an active enrollment. Follow existing patterns from use-reservation-status.ts and use-payment-status.ts for polling and SSE hooks.
